# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

> **CLI:** `secondbrain <command>` is the primary interface (e.g. `secondbrain dev`, `secondbrain doctor`). The `npm run` scripts below are equivalent dev shortcuts.

```bash
npm run build                                   # tsc → dist/
npm run dev                                     # tsx src/index.ts (hot, no build)
npm start                                       # node dist/index.js (run from launchd)
npm run auth:google                             # one-time Google OAuth (Calendar + Tasks)
npm run backfill:google-tasks                   # backfill SQLite tasks → Google Tasks
npm run backfill:imessages -- --all             # backfill chat.db history → imessage_log (search only)
npm run backfill:imessages -- --days 365 --dry  # preview a windowed backfill, no writes

npm run onboard                                 # conversational "Mirror" setup wizard → config/profile.json + context files + .env keys
npm run onboard:dry                             # preview onboarding output into .onboard-dry/, no writes
npm run seed:facts                               # seed owner profile facts + inner-circle people into facts/people (idempotent)
npm run seed:facts:dry                           # preview the seed, no writes
npm run doctor                                  # health check: facts/people present, loops firing, backup fresh (exit 1 if not)

tsx scripts/migrate-memory-to-facts.ts          # one-time legacy memory → facts migration
tsx scripts/backfill-fact-person-ids.ts         # link existing facts to people rows by exact-name match
tsx scripts/test-groups.ts                      # smoke-test group resolution from .env
bash scripts/sync-repos.sh                      # the same script launchd runs every 5 min
```

There is no test runner, linter, or formatter wired up. `tsc` is the only checker — run `npm run build` to typecheck.

## Architecture

### Configuration / Onboarding
The assistant's identity (name, the owner, household members, inner-circle people, and which groups are enabled) is **not hardcoded**. `src/config.ts` loads `config/profile.json` (generated by onboarding, gitignored) as the single source of truth and exposes it to the rest of the codebase. With no profile present it falls back to generic defaults so the repo boots clean out of the box. `src/user-resolver.ts` and `src/lib/system-user.ts` build their users from this config instead of from hardcoded names.

`npm run onboard` (`scripts/onboard.ts`) is a conversational "Mirror" setup wizard that interviews the operator and generates `config/profile.json`, the `context/shared/*` files (identity / voice / profile), `context/seeds/facts.json`, the per-group `context/<group>/CLAUDE.md` files, and the relevant `.env` keys (trigger word, owner/partner users, enabled groups, etc.). `npm run onboard:dry` previews the full output tree into `.onboard-dry/` without writing anything.

Most per-user context is gitignored and generated by onboarding: the per-group `CLAUDE.md` files (admin, personal, finance, work, health, job-search), the shared `identity.md` / `voice.md` / `profile.md`, and `context/seeds/facts.json`. The repo ships generic stand-ins under `context/_examples/`. The synthetic-group context files (brain-pulse, idea-pulse, reflection, content) and `context/shared/security.md` are still committed.

### Channel
The actual channel is **iMessage** (`src/channels/imessage.ts`), polling `~/Library/Messages/chat.db` every 2s and sending replies via AppleScript. There is no WhatsApp code in `src/`. `README.md` (user-facing setup) and `SECOND-BRAIN-ROADMAP.md` (design history for the knowledge/people/reflection layer) agree with this file on the architecture.

**Observing vs. replying are separate decisions (Phase 5).** The poll query no longer filters `is_from_me = 0` — it returns *both* directions. Inside `pollMessages`, every message is first written to `imessage_log` (`logIMessage`), then the **reply path** runs unchanged: outgoing messages (`is_from_me`) `continue` (never reply to ourselves), incoming DMs pass through, incoming group messages still require the configured trigger word (`TRIGGER_WORD`, default `@assistant`). So the agent's reply behavior is byte-for-byte preserved; only the *observation* surface widened. The Phase 5 imessage-daemon reads `imessage_log` and feeds the brain — see Background loops. Note: `startIMessage` seeds the cursor from `MAX(ROWID)`, so the live poller only logs messages from boot forward. Historical threads are filled in separately by `scripts/backfill-imessages.ts` (`npm run backfill:imessages`), which reads chat.db history (decoding the `attributedBody` blob for the ~4% of messages with no plain `text`) and stamps those rows `extracted_at` so they're search-only and not re-fed to the extraction daemon.

### Message → response flow
`src/index.ts` is the only place these pieces meet:

1. `imessage.ts` polls `chat.db`, pulls attachments (image / PDF / audio), and calls the registered handler.
2. `user-resolver.ts` maps sender handle → `User` (with `tone` and `allowedGroups`), built from `src/config.ts` / `config/profile.json` (see Configuration / Onboarding).
3. `group-resolver.ts` maps `remoteJid` → `GroupConfig` (with `tools[]` and `contextPath`). DMs fall through to a synthetic admin group with the full toolset.
4. `router.ts#detectMode` (async) classifies `sync` vs `async`. Calls Haiku (`claude-haiku-4-5`) with a 1.5s timeout; on timeout / API error / missing `ANTHROPIC_API_KEY` it falls back to `detectModeRegex` (the original regex ladder). Result is cached in-memory for 30s. Async tasks get an `async_tasks` DB row and run in the background while the handler returns.
5. `agent.ts#runAgent` runs the Claude tool-use loop (up to `MAX_TURNS=25`, model from `SECONDBRAIN_MODEL` (back-compat: `BROWNBOT_MODEL`) or `claude-sonnet-4-6`). Extended thinking auto-enables for long or "plan/analyze/why/explain"-style prompts (`shouldThink`). On the second-to-last turn, tools are stripped so the model must produce text (currently `agent.ts:257`).
6. `TOOL_LABELS` in `agent.ts` maps tool names → user-facing "📅 Checking calendar…" progress strings, rate-limited to one every 2s via `onProgress`.

### Multimodal inputs
`loadAttachments` in `imessage.ts` pulls one image + one PDF + one audio path per message. PDFs go straight into the Claude message content as a `document` block. Images in a Claude-supported type (`SUPPORTED_IMAGE`: jpeg/png/gif/webp) pass through directly; **anything else (HEIC — the most common iMessage photo format — plus heic-sequence/tiff/avif) is converted to JPEG via `sips`** (`convertImageToJpegBase64`, absolute `SIPS_BIN`, default `/usr/bin/sips`) before becoming an `image` block. Conversion failures log a warning and skip the image (the bot keeps running). Audio is transcribed locally via `src/transcribe.ts` (whisper.cpp + ffmpeg) and prepended to the user text as `[Voice message]: …`. If `whisper-cli`, `ffmpeg`, or `WHISPER_MODEL` is missing, transcription is silently disabled — the bot keeps running. See README "Voice Memos" for install.

### Per-group system prompt
`context-resolver.ts#loadSystemBlocks(group, user, userMessage?)` builds the system prompt fresh on every turn and returns **two segments** — `{ staticPrefix, dynamic }` — so each can get its own prompt-cache breakpoint (see "Prompt caching" below). `loadSystemPrompt` is a thin back-compat wrapper that just joins the two with a newline. The split is deliberate: everything stable for a given `(group, user.tone)` goes in `staticPrefix` (so it caches across messages), and everything that changes per-minute / per-message goes in `dynamic` (so it doesn't bust the static cache).

**`staticPrefix`** (stable per group + user tone), in order:
- `context/shared/identity.md` (the "soul")
- tone/voice: the owner (`tone: 'direct'`) gets `context/shared/voice.md`; the partner (`tone: 'warm'`) gets a one-line warm directive
- **`context/shared/profile.md`** (the always-on owner profile — who they are, what they're optimizing for, how to talk to them, the protected floor, the landmines). Loaded as the `--- About <owner name> ---` block (the name is rendered from config), **gated to `tone: 'direct'`** so it reaches the owner + the system user the scheduler/heartbeat/brain-pulse run as, but never the partner's warm-tone sessions (it contains relationship candor). Granular versions of the same facts are also seeded into the `facts` table (`npm run seed:facts`) for on-demand retrieval; this file is the stable always-on narrative layer and lives in `staticPrefix` so the 5-min prompt cache absorbs its size across an active back-and-forth.
- the group's own `context/<group>/CLAUDE.md`
- `context/<group>/skills/*.md` (each becomes a `### Skill: <name>` block)
- `context/shared/security.md`
- **Tools** — list of *callable* tool names (e.g. `browser_action`, `save_fact`) derived from `toolRegistry`, not the group-key abstractions. Followed by tool-routing rules (snooze/cancel reminders → `snooze_task`/`cancel_task`, person mention → `find_person`/`facts_about`, durable facts → `save_fact`, etc.) and an "Anticipate" nudge. Routing lines that reference the date/retrieval/people blocks say "below"/"in the session context" because those now live in the `dynamic` suffix that follows.

**`dynamic`** (changes per message/minute), in order:
- live session block: group, sender, then **Date reference** (`getDateReference()`) — a precomputed 14-day ET lookup table (`Wed, Jun 3 → 2026-06-03`, with TODAY/tomorrow tags) plus rules for bare day-numbers ("the 13th" = next future occurrence) and an instruction to always emit ISO to calendar/task tools. This replaced the old single prose timestamp because the model was unreliable at date arithmetic; the table makes resolving a date a lookup instead of a calculation. Followed by situation ("Early morning — keep it brief", etc.) and open/overdue task counts.
- **Recent Memory** — `latest_context`, recent `checkpoint_*`, `*_preference`, `current_priorities`, `weekly_schedule_proposal` from the `memory` table, capped at 2000 chars (this is *operational* state — see Persistence)
- **Learned Preferences + Relevant Knowledge + People Context** — three retrieval blocks sharing a single ~2500-char budget (`RETRIEVAL_BUDGET_CHARS` in `context-resolver.ts`). Learned Preferences = high-confidence (`≥0.7`) `feedback`/`preference` facts, always on. Relevant Knowledge = `searchFacts(userMessage)` + `factsAbout(<proper noun>)` for capitalized tokens minus a stopword filter, only when `userMessage` is present. People Context = `peopleSearch(<proper noun>)` + that person's last 2 interactions + 3 facts joined by `person_id`. Blocks are skipped entirely when no hits.
- **Voice Memo Mode** — appended only when `userMessage` starts with `[Voice message]:` and is >300 chars; tells the agent to prefer `save_fact` extraction over a chatty reply.

**Prompt caching.** `agent.ts` sends the two segments as two `system` text blocks, each with `cache_control: { type: 'ephemeral' }` (canonical cache order is `tools → system → messages`). The first breakpoint caches `tools + staticPrefix`, which is byte-identical across messages for a given group/user, so it's reused for the 5-min TTL during an active back-and-forth. The second breakpoint caches `tools + staticPrefix + dynamic`, which is only identical within a single `runAgent` tool loop (the suffix is rebuilt — and the time string changes — between messages). Don't move per-message/per-minute content into `staticPrefix` or you'll silently bust the cross-message cache.

**Important:** the repo-root `CLAUDE.md` (this file) is **not** loaded into the agent's system prompt. Only `context/<group>/CLAUDE.md` files are. Edit those to change the bot's behavior in a given group; edit this file to brief Claude Code.

### Tools and scoping
`src/tools/index.ts` exports `toolRegistry: Record<string, ToolDef[]>`. Each group's `tools[]` lists registry keys; `runAgent` flattens those into the Anthropic `tools` param. MCP servers configured in `mcp-servers.json` are started by `mcp-manager.ts` and their tools merged into the same registry at boot via `registerMcpTools()`. To add a tool, add a module under `src/tools/`, register it in `tools/index.ts`, and add its key to the relevant group(s) in `group-resolver.ts` (and the system-user group config in `scheduler.ts` / `heartbeat.ts` if it should run from scheduled jobs).

Notable tool surfaces beyond the obvious (calendar / spark / github / linkedin / finance):
- **`memory`** — legacy `remember`/`recall`/`memory_checkpoint` plus structured-fact tools `save_fact` / `search_facts` / `facts_about`. `recall` falls back to fact search when the legacy key misses.
- **`people`** — `find_person` / `note_about_person` / `recent_interactions` / `log_interaction` / `who_to_reach_out_to` (reach-out radar: `getStaleContacts` = prior contacts gone cold + `getDormantLeads`). Backed by the `people` + `person_emails` + `person_phones` + `interactions` tables.
- **`messages`** — `search_messages` (agent-facing search over `imessage_log` via `searchIMessages`, by keyword and/or person; newest-first). Only covers messages observed since boot — not a historical archive. Admin/DM groups only.
- **`recall`** (admin/DM only) — `recall_memory(subject?)` (`src/tools/recall.ts`). One call that aggregates **everything** stored about a subject — facts (`searchFactsBroad` + `factsAbout`), people + recent interactions, open tasks (title/notes match), and iMessages — bypassing the `RETRIEVAL_BUDGET_CHARS` truncation in `loadSystemPrompt`. Omit `subject` for a tracked-everything overview (`getTaskStats` + open/overdue tasks + facts-by-type + recent `memory` notes). The system prompt (Tool Routing) + `context/admin/CLAUDE.md` instruct the agent to call it **before** ever claiming it has no note/fact/reminder — the fix for "the assistant says it doesn't have it but the data's there". `searchFactsBroad` (in `db.ts`) is FTS-first with a `LIKE '%token%'` fallback so near-miss/partial-word queries that FTS drops still match.
- **`tasks`** — `create_task` / `list_tasks` / `update_task` / `complete_task` / `cancel_task` / `snooze_task` / `get_task_summary` / `get_schedulable_tasks` / `link_task_to_event` / `unlink_task_from_event`. `snooze_task` suppresses heartbeat reminders without moving `due_date`; `cancel_task` is distinct from `complete_task`.
- **`browser`** — `browser_action` (full multi-action API), `browser_navigate` (convenience alias for navigating to a URL), `clip_to_facts` (saves the current tab as a fact + returns extracted text for further structuring).
- **`actions`** (admin only) — `propose_action` / `confirm_action` / `cancel_action` / `list_pending_actions`. The propose → confirm → execute gate for money-spending / commitment actions. **The executors are deliberately NOT in the registry** — `EXECUTORS` in `src/tools/actions.ts` (slice 1: `browser_reorder` → `runBrowserReorder` in `src/tools/browser-reorder.ts`) runs *inside* `confirm_action`, so the agent has no callable path that skips the gate. Kill switch + spend caps live in `src/lib/spend-cap.ts` (`checkActionsEnabled` / `checkSpendCap`), called by both propose and confirm. Reply grammar (`go`/`edit`/`cancel #action:N`) is a system-prompt convention in `context/admin/CLAUDE.md`, not a parser.
- **path guardrails** — `src/tools/path-utils.ts` exports `resolveSafePath`, `validateRepoName`, `slugifyForAnalysis`, `subjectFromAnalysis`. Used by `github` / `claude-code` / `career-os` to reject path traversal, allowlist repo roots, block secret-file patterns (`.env*`, `*.pem`, etc.), and produce consistent JD analysis slugs.

`src/tools/web.ts#assertSafeUrl` rejects non-`http(s)` URLs and any private/loopback host; curl invocations pin `--proto =http,https` so redirects can't escape.

### Persistence
Single SQLite file `secondbrain.db` (back-compat: `brownbot.db`) (WAL mode), managed by `src/db.ts`. Tables:

- **`messages`** — conversation history per group. `getMessagesSince(timestamp)` powers the nightly reflection.
- **`async_tasks`** — background work queued by the async-mode handler.
- **`memory`** — per-group key/value, for *operational state* (e.g. `last_meeting_prep_event_id`, `last_notification_clear`, `last_reflection_at`, `morning_brief_<date>`) and the legacy "Recent Memory" prompt block. Knowledge moved to `facts`.
- **`tasks`** — the canonical task list. `create_task` syncs to Google Tasks on the owner's phone (no Apple Reminders). Task `assignee` values are `owner` / `partner` (plus the unchanged `secondbrain` bot-sentinel). Phase 7 added `snoozed_until` (suppress without moving `due_date`), `last_surfaced_at` + `surface_count`. **Organic reminders** replaced the flat re-ping: `surface_count` now drives an *escalating backoff* (`BACKOFF_LADDER_HOURS`, default ~1d/2d/4d/weekly via `HEARTBEAT_BACKOFF_HOURS`) so a task you keep ignoring goes quiet on its own; after `RETIRE_AT_SURFACE_COUNT` surfaces (`HEARTBEAT_RETIRE_AFTER`, default 4) it leaves the surfacing queries and routes to `getTasksNeedingDecision` (the morning "kill it or commit" question), then `markTaskRetired` sets `retired_at` to drop it entirely. `snoozeTask` / a `due_date` change call `resetTaskSurfacing` (clear `retired_at`, zero `surface_count`) so a touch restarts the cycle fresh. (`HEARTBEAT_RESURFACE_HOURS` is retired in favor of the ladder.)
- **`facts` + `facts_fts`** — atomic `(subject, predicate, object)` knowledge store with SQLite FTS5. Per-type supersession in `saveFact`: `preference`/`decision`/`metric` overwrite prior active rows on `(subject, predicate)`; `commitment`/`feedback`/`fact` append. `searchFacts` sanitizes user text through `ftsTokenize` before MATCH and filters `active=1` + unexpired in SQL. `subject` and `predicate` are normalized to lowercase on write; index uses `COLLATE NOCASE`. Optional `person_id` links facts to a row in `people` (auto-bound on exact-name match).
- **`people` + `person_emails` + `person_phones` + `interactions`** — canonical person records (name/company/role/linkedin_url/relationship), a normalized email map (PRIMARY KEY COLLATE NOCASE), a normalized **phone map** (`person_phones`, keyed on the last-10-digits form from `src/lib/phone.ts#normalizePhone`), and an interaction log. `upsertPerson` accepts `emails[]` + `phones[]` and dedups across emails → phones → `linkedin_url`. `findPersonByPhone` / `findPersonByEmail` resolve a person from a single handle. Populated automatically by hooks in calendar / spark / linkedin tools, by the iMessage daemon (which links incoming **sender handles** to known people via `findPersonByPhone`/`findPersonByEmail`), and seeded from Apple Contacts by `scripts/import-contacts.ts` (`npm run import:contacts`, also nightly via `launchd/com.secondbrain.contacts-sync.plist`). Surfaced in the People Context prompt block.
- **`actions`** (Tier 2 Phase 1) — real-world actions that spend money or commit to a person (orders/bookings/calls), staged behind a propose → confirm → execute gate. One row per action; status transitions in place (`proposed` → `confirmed` → `executing` → `done`/`failed`, or `proposed` → `cancelled`). `payload_json` is the executor's args, frozen at propose time — the audit-grade snapshot of exactly what runs. `estimated_cost_cents` is set at propose and is the anchor the executor drift-checks (>5% abort); `actual_cost_cents` (whatever the receipt shows at execute time — refunds/back-orders not tracked) is what counts toward the spend cap. Accessors in `db.ts`: `proposeAction` / `getAction` / `listPendingActions` / `listRecentActions` / `updateActionProposal` (edit-while-proposed) / `confirmAction` / `markActionExecuting` / `markActionDone` / `markActionFailed` / `cancelAction` / `getDailyActionSpendCents` / `getWeeklyActionSpendCents` (the last two bounded by ET calendar day/week via `lib/time-et.ts#startOfTodayET`/`startOfWeekET`, counting only `status='done'` rows).
- **`imessage_log`** (Phase 5) — passive capture of *every* observed iMessage (both directions, all chats), independent of the configured trigger-word reply trigger. `logIMessage` does `INSERT OR IGNORE` keyed on `rowid_src` (the chat.db ROWID) so re-polling is idempotent. `extracted_at` is the cursor: NULL until the imessage-daemon processes a row. Accessors: `logIMessage` (live write path, called from `imessage.ts`), `backfillIMessage` / `backfillIMessages` (historical write path — INSERT OR IGNORE with `extracted_at` pre-stamped), `getUnextractedIMessages(limit)` / `markIMessagesExtracted(ids)` (daemon read/advance), `searchIMessages` (agent-facing search via the `messages` tool). Senders are phone numbers / emails; the imessage-daemon now links them to people via the `person_phones` / `person_emails` maps (`findPersonByPhone`/`findPersonByEmail`), so once Apple Contacts seeds a person with both a phone and an email, iMessage activity dedups against email-keyed rows. Residual gap: a handle with **no** Contacts/CRM match is not auto-seeded as a new person (we don't create nameless phone-only rows) — run `npm run import:contacts` to backfill.
- **`email_extraction_log`** (Tier 2) — dedup cursor for the inbox-signal-daemon. Unlike `imessage_log` there is no upstream poller filling it; email lives only in Spark, so the daemon enumerates a recent window itself and records every Spark message ID it has *seen* here (extracted or dropped). `INSERT OR IGNORE` on the `UNIQUE message_id` (Spark's list "ID" column, stored as text) makes re-enumerating an overlapping `newer_than` window idempotent. Accessors: `isEmailExtracted(messageId)` (skip-already-seen) / `markEmailExtracted({message_id, signal_count, …})` (advance the cursor; returns true if first-seen). Cursor model is "have we processed this message_id", not `id > N`.

### Background loops
- `scheduler.ts` — `node-cron` jobs that invoke `runAgent` with the system user (the owner, admin tone) and DM the result. Daily inbox triage (08:00 ET), calendar prep (06:30 — prepends the previous night's morning brief if one is staged, and is the once-daily home for routine task surfacing: `buildMorningTaskContext` feeds overdue + due-today into the agent to weave in contextually, and routes "needs a decision" tasks — those past the retire threshold — into one pointed kill-it-or-commit question), evening wrap-up (18:00 weekdays), Health evening check-in (21:00, only if `GROUP_HEALTH` is set), alive ping (09:00 — short DM built by `formatAlivePing(runHealthCheck())` in `src/doctor.ts`: brain stats when healthy, plus a "needs attention" list when a check is stale — unseeded facts, a reflection/backup that hasn't run, a dead daemon tick), nightly reflection (22:00 ET — see below). **Finance live-sync:** a deterministic (no-LLM) Plaid pull (`syncPlaidTransactions` in `tools/finance.ts` → `POST /api/plaid/sync-transactions`) runs **every 6h** to keep the finance backend's Supabase DB fresh — the finance read tools (`get_account_balances` etc.) only ever read that DB, never call Plaid, so without this the numbers go stale. A **daily 07:00 ET metric refresh** then syncs and re-stamps the `bmm` runway/burn/balance `metric` facts with `valid_until ≈ 2 days` (so chat reflects current numbers within a day, not just after the Sunday run). Weekly: household overview, job-search brief, GitHub summary, finance summary (Sunday 10:00 — syncs Plaid first, then writes runway/burn/balance as `metric` facts with `valid_until = next Sunday` for the longer narrative checkpoint), work-project brief, task scheduling.
- **Nightly reflection** — synthetic `REFLECTION_GROUP` (defined in `group-resolver.ts`, never resolved via `resolveGroup`). 22:00 ET cron reads everything new across groups via `getMessagesSince(last_reflection_at)`, caps per-group input (50 messages × 500 chars each), runs `runAgent` with cross-cutting tool scope (`spark`, `calendar`, `finance`, `github`, `memory`, `tasks`, `people`). Agent calls `remember('morning_brief_<TOMORROW-ET>', …)`. The 06:30 calendar prep reads that key, prepends it, and `deleteMemory`s it.
- `heartbeat.ts` — proactive 30-min check-ins. **Organic reminders (the interrupt vs. ambient split):** the 30-min pulse is the *interrupt* channel and `heartbeatTaskCheck` now surfaces **only 24h+ critical overdue** — routine overdue / due-soon moved to the once-daily morning brief (06:30, see `scheduler.ts`). Still calls `markTaskSurfaced` per surfaced task and caps at 5. Reply hint at the bottom of each ping ("snooze #N 3 days", "cancel #N", "done #N") teaches the agent the routing. Honors quiet hours (21:00–07:00 ET) via the surfacing filter; `isQuietHours` (from `src/lib/time-et.ts`) is still used by the calendar/async branches. Calendar branch (a) (30-min external-meeting prep) was removed in Tier 1 Phase 1 — that job moved to the meeting daemon (Phase 4); the heartbeat now only handles "time to leave" and conflict detection.
- `brain-pulse.ts` — proactive 11:00 + 16:00 ET scan of the second brain. Calls `getStaleCommitments` (commitments aged >7d with `completed_at IS NULL`), `getExpiringFacts` (`valid_until` in next 7d, excluding `metric` type which auto-supersedes weekly), and `getDormantLeads` (relationship='lead', `last_contact` >60d). Dedup via `last_surfaced_at` on `facts`/`people` with window `PULSE_RESURFACE_HOURS` (default 18h). Routes through the synthetic `BRAIN_PULSE_GROUP` (tools: `memory`, `tasks`, `people`, `calendar` — NOT `facts`, which isn't a real registry key). Reply-hint grammar is namespaced — `done #fact:N` / `extend #fact:N 30d` / `reached out #person:N` / `still open #fact:N` — to avoid colliding with the existing `done #N` task grammar. Routing rules live in `context/admin/CLAUDE.md`. Honors quiet hours.
- `idea-pulse.ts` — proactive 10:00 + 15:00 ET ping where the assistant **offers help and pitches ideas** (grounded + creative), as opposed to brain-pulse which surfaces aging rows for a status reply. Pulls a snapshot (`getOpenTasks`, `getDormantLeads`, `getFactsByType(['decision','commitment','preference'])`), hands it to `runAgent` via the synthetic `IDEA_PULSE_GROUP` (tools: `memory`, `tasks`, `people`, `calendar`), and asks for 2-4 in-voice lines that invite a reply. Dedup is simple: the last batch of pitched ideas is stored in `memory` under group `idea-pulse` / key `recent_ideas` (rolling 1500-char tail) and fed back into the prompt as "don't repeat these". Agent replies `IDEA_CLEAR` to suppress. Kill switch `IDEA_PULSE_ENABLED` (default `true`). Honors quiet hours. Context/format in `context/idea-pulse/CLAUDE.md`.
- `scripts/imessage-daemon.ts` (Phase 5) — separate launchd KeepAlive daemon (`launchd/com.secondbrain.imessage-daemon.plist`), modeled on the meeting daemon, NOT a cron. Every `IMESSAGE_DAEMON_INTERVAL_MS` (default 10 min) it pulls `getUnextractedIMessages`, runs a **Haiku pre-filter** (`SECONDBRAIN_ROUTER_MODEL`) to drop chatter, then a **Sonnet** (`SECONDBRAIN_MODEL`) structured-JSON extraction, then writes back via the same db helpers the meeting daemon uses: commitments the owner made → `saveFact(fact_type:'commitment')` (Brain Pulse surfaces them automatically), deadlines → `createTask(source:'imessage-daemon')` + Google push, people → `upsertPerson` + `addInteraction(channel:'imessage')`, decisions → `saveFact(fact_type:'decision')`. It marks **all** pulled rows extracted (candidates + filtered-out) so the cursor advances. There is intentionally no new surfacing layer — facts flow into the existing Brain Pulse / reflection. Run `npx tsx scripts/imessage-daemon.ts --test` for a single tick. **Liveness:** each KeepAlive daemon stamps `<name>_last_tick` into the `memory` table after every successful tick (in `runDaemon` for imessage/inbox-signal; meeting-daemon's own loop) so `runHealthCheck` / the 09:00 alive ping can flag a daemon whose process has died (>2h stale). Test ticks never stamp.
- `scripts/inbox-signal-daemon.ts` (Tier 2) — separate launchd KeepAlive daemon (`launchd/com.secondbrain.inbox-signal-daemon.plist`), modeled on the imessage daemon, NOT a cron. The complement to the read-only 8:00 inbox triage (`scheduler.ts`): where triage *summarizes*, this daemon *acts*. Every `INBOX_SIGNAL_INTERVAL_MS` (default 15 min) it (1) enumerates a `newer_than:INBOX_SIGNAL_WINDOW` (default 2d) email window from Spark via `sparkRaw` and drops `message_id`s already in `email_extraction_log`, (2) runs a **Haiku pre-filter** (`SECONDBRAIN_ROUTER_MODEL`) to keep only delivery / bill / payment-failure / registration / document signals, (3) reads each survivor's full thread and runs a **Sonnet** (`SECONDBRAIN_MODEL`) structured-JSON extraction, then **auto-creates reversible artifacts**: deliveries + registrations → `createCalendarEventRaw` (factored out of the `create_event` tool in `tools/calendar.ts`; all-day when no time window), bills → `createTask(group_id:'finance', source:'inbox-signal-daemon')` + Google push, payment failures → high-priority `createTask` (due today) + an urgent line in the digest, documents → `saveFact(fact_type:'reference')`. It then sends **one digest DM** of everything created (payment failures first) — the "+ notify" half of the trust model — and `markEmailExtracted`s every enumerated row so the cursor advances. It never spends money or replies; those stay behind the Tier 2 actions gate. Surfacing is otherwise free (tasks ride the heartbeat, facts ride Brain Pulse). `--test` does one tick with **no writes** (no DB / calendar / DM — prints intended artifacts) against live Spark; run `npm run inbox-signal-daemon:test`. Known gaps: enumeration only reads page 1 (a burst of >`BATCH` emails in one window could push an item off-page until older mail ages out); the `message_id` dedup stops reprocessing the *same* email but two different emails about one shipment ("shipped" + "out for delivery") can double-book — a `(carrier, date, tracking)` secondary dedup is a v2 follow-up; "documents" captures the Drive/attachment *reference* only (no fetch — the daemon runs in the bot process, not an MCP session).
- **Where scheduled jobs live**: `scheduler.ts` (daily/weekly cron + nightly reflection), `heartbeat.ts` (30-min), `brain-pulse.ts` (11:00 + 16:00 ET). Future Phase 2/3 additions: `hygiene.ts` (Mon 07:30 ET), `content-flywheel.ts` (Sat 10:00 ET). Phase 4 meeting prep/debrief runs as a separate launchd KeepAlive daemon (`scripts/meeting-daemon.ts`), not a cron; Phase 5 iMessage extraction is a second such daemon (`scripts/imessage-daemon.ts`).
- `browser-bridge.ts` — WebSocket server the Chrome extension connects to. Optional token auth via `BROWSER_BRIDGE_TOKEN`; the extension sends `{type:'auth', token}` as its first frame when configured. Optional Chrome extension origin pin via `BROWSER_EXTENSION_ID`. Default-open if no token is set (preserves legacy setups). See `browser-extension/SETUP.md`.
- `dashboard.ts` — Node's built-in `http` server bound to `127.0.0.1:4000` (configurable via `SECONDBRAIN_DASH_PORT`, back-compat: `BROWNBOT_DASH_PORT`). Read-only HTML view over facts, the full task list (open/overdue/snoozed/recently-done), reminders & operational state (`memory` table), people, interactions, recent iMessages, aging commitments/expiring facts, and the actions queue. `GET /?q=…` runs a server-side search across facts (`searchFactsBroad`), people, tasks, and messages; the dashboard view auto-refreshes every 30s (`<meta http-equiv="refresh">`). No auth — loopback only; reach from phone via Tailscale. No client framework — all server-rendered HTML.
- **Nightly backup** — `launchd/com.secondbrain.backup.plist` at 03:00 runs `scripts/backup-db.sh`, which uses `sqlite3 .backup` (online API, torn-write safe under `KeepAlive`) to write `~/.secondbrain/backups/secondbrain.db.YYYYMMDD-HHMMSS` and prunes anything older than 14 days.
- **Nightly Contacts sync** — `launchd/com.secondbrain.contacts-sync.plist` at 04:00 runs `scripts/import-contacts.ts`, reading every `~/Library/Application Support/AddressBook/Sources/*/AddressBook-v22.abcddb` (read-only) and `upsertPerson`-ing each named contact's emails + phones. Idempotent (re-runs merge, not duplicate). Requires the process to have Full Disk Access (same as chat.db). Run once manually to bootstrap: `npm run import:contacts` (`--dry` to preview).

### Auto-sync (mac mini deployment)
`scripts/sync-repos.sh` (driven by `launchd/com.secondbrain.sync.plist`, every 5 min) `git pull`s every repo Second Brain reads from. Repos in `CONTENT_REPOS` are pulled silently; repos in `SERVICE_REPOS` (e.g. `secondbrain-seed`, the finance backend) kickstart their launchd agent when their own code updates. Second Brain also rebuilds TypeScript on its own update. So pushing to `main` of this repo on a dev box deploys to the mac mini within 5 minutes.

## Gotchas

- `import` paths use `.js` extensions even for `.ts` source — required by NodeNext ESM resolution. Don't "fix" them.
- `agent.ts` strips tools on the second-to-last turn (`turn === MAX_TURNS - 2`, currently `agent.ts:257`). If you raise `MAX_TURNS`, the cutoff stays correct because it's relative.
- Group resolution falls through to admin for any DM (phone or email sender). Permission checks live in `user-resolver.ts#isAllowed`, not in group resolution.
- `chat.db` is read-only — never write to it. Outbound messages go through AppleScript (`Messages` app), which has chunking at 15000 chars in `sendMessage`.
- `WHISPER_MODEL` default in `transcribe.ts` is `~/.cache/whisper/ggml-small.en.bin`, but the documented install path is `~/whisper-models/ggml-small.en.bin`. The env var is the source of truth — make sure `~/.zprofile` exports it so launchd sees it.
- `memory` vs `facts`: `memory` is operational key/value state (counters, dated keys like `morning_brief_<date>`, conversation checkpoints). `facts` is durable knowledge with retrieval. When in doubt about a new save: if there's a clear subject (a person's name, a project name, the owner), use `saveFact`; if it's a runtime flag or a dated brief, use `setMemory`.
- Heartbeat/morning task surfacing is decay-aware. `getOverdueTasks` / `getTasksDueSoon` (in `db.ts`) filter out snoozed, retired, and not-yet-due-for-resurface tasks (escalating backoff keyed on `surface_count`), AND drop tasks past `RETIRE_AT_SURFACE_COUNT` (those go to `getTasksNeedingDecision`). Anywhere you want the *full* truth (dashboard, daily brief, `get_task_summary`), use the `*All` variants. Reusing the filtered queries in user-facing summaries will silently hide tasks the user expects to see. Note the only writers that should advance the ladder are the surfacing paths (`markTaskSurfaced`); user actions (snooze/reschedule) must `resetTaskSurfacing` so the cycle restarts.
- `router.ts` exposes `detectMode(text): Promise<Mode>` — one Haiku call classifies sync vs async (output is a single word `sync`/`async`), with a regex ladder (`detectModeRegex`) as the fallback on `ANTHROPIC_API_KEY` missing / Haiku failure / timeout, plus a ~30s in-memory cache. `index.ts` fires a **fixed receipt ack** (`RECEIVED_ACK = 'On it.'`) the instant a message lands, independent of mode. (The earlier per-message LLM-generated ack — `routeMessage`/`RouteResult.ack`/`getSmartAck` — was removed: the dynamic acks drifted out of context, so a single reliable "received" signal replaced them. `index.ts` is the only place to change the ack text.)
- `loadSystemPrompt` now takes an optional `userMessage` argument. Callers that have it should pass it (so Relevant Knowledge + People Context blocks render). Scheduler/heartbeat callers pass `undefined` and that's fine — their prompts are system-authored.
- Path-touching tools route through `src/tools/path-utils.ts`. Don't add a new file-reading tool that bypasses `resolveSafePath` / `validateRepoName` — the guardrails are there to prevent the agent from grepping `~/.ssh/`, your other repos' `.env` files, etc.
- `spawn_claude_code` (`src/tools/claude-code.ts`) pins the `claude` binary by **absolute path** (`CLAUDE_CODE_BIN`, default `/opt/homebrew/bin/claude`), not bare `spawn('claude')`. launchd starts Second Brain with PATH `/usr/bin:/bin:/usr/sbin:/sbin` (no Homebrew), so a PATH-relative spawn fails with ENOENT. Same caveat applies to any new tool that shells out to a Homebrew-installed binary.
